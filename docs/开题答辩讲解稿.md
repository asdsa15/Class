## 第1页｜封面

各位老师好，我的毕业设计题目是《基于 Python Web 的课堂专注度分析系统设计与实现》。

本课题主要研究如何利用 YOLOv8 对课堂中的学生行为进行识别，在此基础上建立专注度评价方法，并通过 Python Web 技术将模型能力封装成一个可以实际使用的课堂专注度分析系统。

整个系统主要采用 YOLOv8、Python、FastAPI、MySQL 和 WebSocket 等技术。

今天我主要从研究背景、研究内容、技术框架可行性、具体实现路径以及后续计划几个方面进行汇报。

## 第2页｜目录

本次汇报主要分为五个部分。

第一部分介绍课题的研究背景和意义；第二部分介绍相关研究现状以及目前存在的问题；第三部分介绍本课题的研究目标和主要内容；第四部分重点介绍技术框架的选择、可行性以及具体实现路径；最后介绍项目计划和预期成果。

## 第3页｜研究背景

课堂专注度是反映学生课堂学习状态的重要指标。

传统情况下，教师通常通过课堂观察、提问或者课后反馈判断学生的学习状态，这种方式比较依赖教师个人经验，而且很难持续记录整个课堂的变化情况。

例如，一节课前十分钟和后十分钟学生的状态可能存在明显差异，但是人工记录很难形成连续的数据。

因此，我希望利用计算机视觉技术，把课堂中的一些可识别行为进行自动分析，再把这些行为转换成能够量化的专注度指标，为教师进行课堂分析提供辅助数据。

这里需要说明的是，本系统的定位是**辅助分析**，而不是完全替代教师对学生的评价。

---

## 第4页｜研究意义

本课题主要有三个方面的意义。

第一是教学意义。通过对课堂行为进行持续分析，可以为教师提供更加直观的课堂状态数据，例如不同时间段的专注度变化。

第二是技术意义。本课题尝试把 YOLOv8 目标检测模型和 Python Web 服务结合起来，不只是完成一个模型识别实验，而是进一步解决模型如何被 Web 系统调用、结果如何保存和展示的问题。

第三是应用意义。模型产生的检测结果经过处理后，可以保存到数据库中，从而形成历史课堂数据，为后续查询、统计和分析提供基础。

---

## 第5页｜相关研究现状

目前课堂专注度分析大致可以从人工评价、传统计算机视觉以及深度学习三个方向理解。

人工评价的优点是简单直接，但是主观性较强，而且难以连续量化。

传统计算机视觉方法可以通过人工设计的特征进行识别，但是面对课堂这种多人、遮挡、光照变化比较明显的环境时，适应能力有限。

近年来深度学习目标检测方法的发展，使课堂行为自动识别具备了更好的技术基础。YOLO 系列模型具有较好的检测速度，因此比较适合进一步应用到课堂视频分析中。

但是仅仅完成行为检测还不够。真正形成一个课堂专注度分析系统，还需要解决两个问题：第一，如何把行为检测结果转化成专注度；第二，如何把 AI 模型集成到 Web 系统中形成完整业务流程。

这也是本课题主要要解决的问题。

---

## 第6页｜研究目标

本课题的总体目标，是设计并实现一个基于 Python Web 的课堂专注度分析系统。

具体来说，首先利用 YOLOv8 识别课堂中的典型行为；然后根据行为数量和行为权重计算课堂专注度；接下来使用 FastAPI 将模型能力封装为 Web 服务，并通过 MySQL 保存用户、课程、课堂和分析结果等数据。

同时，系统需要考虑图片、视频以及实时数据等不同输入方式，因此会使用普通 HTTP API 处理一般请求，并使用 WebSocket 支持实时检测场景。

最终形成从数据输入、模型识别、专注度计算，到数据存储和结果分析的一套完整技术流程。

---

## 第7页｜研究内容

本课题可以分成四个技术层次。

第一层是 AI 模型层，主要研究 YOLOv8 的课堂行为检测，包括数据集准备、模型训练、验证以及 Precision、Recall、mAP 等指标评价。

第二层是专注度算法层。YOLOv8 输出的是行为类别和检测结果，并不会直接告诉我们一个百分比形式的专注度，因此需要进一步统计不同类别的人数，再通过行为权重进行计算。

第三层是 Web 系统层，主要使用 FastAPI 提供 API 服务，并利用 WebSocket 处理实时检测。

第四层是数据层，使用 MySQL 和 SQLAlchemy 保存系统业务数据以及课堂分析数据。

这四层最终组合成一个完整系统。

---

# 技术框架重点讲解

## 第8页｜总体技术框架

这一页是整个技术方案的核心。

从整体架构来看，最上层是 Web 前端，负责和用户交互；下面是 FastAPI 服务层，负责接收请求、进行身份认证、调用业务逻辑以及返回结果；再下面是 AI 分析层，负责调用 YOLOv8 和 OpenCV 完成图像分析，并根据检测结果计算专注度；最下面是 MySQL 数据层，负责数据持久化。

选择这种架构主要是因为各项技术之间具有比较好的兼容性。

YOLOv8 本身就是 Python 生态中的模型，可以直接在 Python 后端中调用；FastAPI 同样基于 Python，因此不需要额外增加一个跨语言服务层。

这样做的好处是技术链路比较简单：

> **前端 → FastAPI → AI 模型/业务逻辑 → MySQL。**

对于毕业设计来说，这种架构既能够体现 AI 与 Web 的结合，也不会因为系统拆分过度而增加实现难度。

---

## 第9页｜为什么选择 YOLOv8

YOLOv8 主要解决的是系统中的视觉识别问题。

课堂场景具有多人同时出现的特点，所以模型不仅需要判断有没有学生，还需要同时识别不同学生的行为类别。

YOLOv8 属于一阶段目标检测模型，具有比较好的检测速度，并且 Python 生态成熟，可以和 PyTorch、OpenCV 等工具直接结合。

因此，在本课题中，YOLOv8 的职责可以明确为：

> **输入课堂图像或视频，输出学生行为类别、位置以及对应的置信度。**

需要特别说明，YOLOv8 不负责直接计算专注度，它只负责提供后续算法所需要的行为数据。

---

## 第10页｜为什么选择 FastAPI

FastAPI 主要解决的是 AI 模型如何被 Web 系统调用的问题。

如果只有 YOLOv8 模型，那么用户需要通过 Python 程序才能使用模型，普通教师无法直接操作。

所以需要一个 Web 后端，把模型封装成 API。

选择 FastAPI 的原因主要有三个。

第一，FastAPI 本身基于 Python，与 YOLOv8 的集成比较自然。

第二，它可以比较方便地定义 REST API，例如上传图片后调用检测接口。

第三，它原生支持异步编程和 WebSocket，因此后续实现实时检测时不需要再引入完全不同的服务框架。

因此 FastAPI 在整个架构中承担的是“连接前端、业务逻辑和 AI 模型”的角色。

---

## 第11页｜为什么选择 MySQL

系统运行过程中会产生很多结构化数据，例如用户、课程、课堂、检测记录以及专注度记录。

这些数据之间存在明确的关系，例如一个教师可以有多个课程，一门课程可以产生多次课堂记录，一次课堂又可以产生多条检测记录。

所以采用关系型数据库更合适。

MySQL 技术成熟，支持事务、索引和关系约束，同时 SQLAlchemy 可以作为 Python 后端和 MySQL 之间的 ORM 层。

这样程序不需要在大量业务代码中直接拼接 SQL，而是通过模型对象操作数据库，可以提高代码的可维护性。

因此 MySQL 主要解决系统的**数据持久化和历史数据管理问题**。

---

## 第12页｜为什么使用 WebSocket

普通 Web API 更适合一次请求对应一次响应的场景，例如登录、课程查询或者上传一张图片进行检测。

但是实时课堂检测不一样。实时检测需要不断传输视频帧，并持续返回模型检测结果。

如果每一帧都重新建立 HTTP 请求，通信开销会比较大，也不利于实时交互。

因此这里使用 WebSocket 建立长连接。

基本流程就是：

> 浏览器持续发送图像帧 → FastAPI WebSocket 接收 → YOLOv8 推理 → 计算行为和专注度 → 服务端返回结果。

所以 WebSocket 解决的是系统中的**实时数据传输问题**。

---

# 实现路径重点讲解

## 第13页｜系统实现路径

系统的实现不会一次性全部完成，而是按照从底层到上层的方式逐步实现。

第一步是准备课堂行为数据，并对 YOLOv8 模型进行训练和验证。

第二步是把模型推理能力封装成独立的检测模块，使输入一张图片或者一段视频后能够得到统一格式的检测结果。

第三步是在检测结果基础上进行行为统计，并设计专注度计算方法。

第四步使用 FastAPI 把检测和专注度计算封装成接口。

第五步建立 MySQL 数据库，将用户、课程、课堂以及检测结果保存下来。

第六步再开发 Web 前端，通过 API 获取后端结果。

最后进行前后端联调、模型测试、数据库测试和权限测试。

所以整个实现路径可以概括为：

> **模型 → 算法 → 后端 → 数据库 → 前端 → 联调测试。**

这样分阶段实现可以降低开发难度，也便于出现问题时定位是模型、算法还是 Web 服务的问题。

---

## 第14页｜AI 到 Web 的完整数据流

这一页重点解释数据到底是怎么流动的。

首先，系统从课堂图片、视频或者摄像头获取数据。

然后通过 OpenCV 完成读取、格式转换以及必要的预处理。

之后把数据交给 YOLOv8，模型输出行为类别、位置和置信度。

后端对这些结果进行统计，例如统计举手、阅读、写作、使用手机、低头等行为的数量。

然后根据行为权重计算专注度。

计算完成后，结果通过 FastAPI 返回给前端，同时把需要长期保存的数据写入 MySQL。

最后前端只负责展示后端已经处理好的数据。

这里最重要的一点是：

> **专注度不是 YOLOv8 直接识别出来的，而是由“行为检测结果 + 专注度算法”共同得到的。**

这样可以把模型和评价算法解耦，后续如果修改专注度计算方式，不需要重新设计整个 Web 系统。

---

## 第15页｜专注度算法实现路径

专注度算法的基本思想是把不同课堂行为赋予不同权重。

例如阅读和写作通常属于与学习任务直接相关的行为，因此可以设置较高权重；使用手机等行为对当前学习任务的关联性较低，可以设置较低权重；低头这种行为存在多种可能性，因此不能简单认为完全不专注。

计算时首先统计各类行为人数，再根据对应权重进行加权平均，最终得到一个百分比形式的专注度。

公式可以概括为：

> 专注度 = 各类行为人数 × 对应权重的总和 ÷ 检测总人数。

这里的权重属于本系统当前的初始设计参数，并不是行业统一标准。

后续需要通过实验数据、不同权重方案对比以及必要的人工评价结果来验证其合理性。

这样可以避免把一个主观假设直接当成科学结论。

# 可行性重点讲解

## 第16页｜项目可行性分析

从技术角度来看，本课题具有较好的可行性。

第一是技术可行性。YOLOv8、OpenCV、FastAPI、SQLAlchemy 和 MySQL 都具有比较成熟的 Python 生态，技术之间可以直接进行集成，不需要开发底层框架。

第二是数据可行性。目前已经具备课堂行为识别的数据和模型基础，可以继续进行模型验证和优化。

第三是工程可行性。系统可以按照模型层、业务层、Web 层和数据层进行模块化设计，各部分职责比较明确。

第四是开发周期可行性。当前项目已经具备 Web、数据库和检测功能基础，因此后续主要集中在模型指标整理、专注度参数验证、系统测试和论文整理，而不是从零开始开发。

综合来看，本课题不存在明显的技术路线障碍。

## 最后一页｜总结

本课题主要解决的是课堂专注度难以连续、客观量化的问题。

从技术路线来看，YOLOv8 负责课堂行为识别，专注度算法负责把行为转换成量化指标，FastAPI 负责提供 Web 服务，WebSocket 负责实时通信，MySQL 负责数据持久化。

因此整个系统形成了一条比较清晰的技术链路：

> **课堂数据 → YOLOv8 → 行为统计 → 专注度计算 → FastAPI → MySQL → Web 分析。**

目前技术路线具有可行性，后续重点是模型效果验证、专注度算法优化和系统测试。
